## สิ่งที่กำลังจะสร้าง

Kubernetes **1.36.3** แบบ HA บน Oracle Linux 9.8 — control plane 3 เครื่อง (stacked etcd)
worker 3 เครื่อง โดยมี Cilium ทำหน้าที่ CNI, แทน kube-proxy และจ่าย LoadBalancer IP ในตัวเดียว

```
                        ┌──────────────────────────────┐
   client ──────────────►  VIP 192.168.50.100:8443     │  keepalived + HAProxy
                        │  (ลอยอยู่บน master ตัวใดตัวหนึ่ง) │  เป็น systemd service
                        └───────────────┬──────────────┘
                    ┌───────────────────┼───────────────────┐
                    ▼                   ▼                   ▼
              master01 .101       master02 .102       master03 .103
              apiserver:6443      apiserver:6443      apiserver:6443
              etcd                etcd                etcd
                    └───────────────────┼───────────────────┘
                    ┌───────────────────┼───────────────────┐
                    ▼                   ▼                   ▼
              worker01 .104       worker02 .105       worker03 .106
```

**แผนผังข้างบนเป็นเส้นทางของ control plane เท่านั้น** — ทราฟฟิกของผู้ใช้จริงเดินอีกเส้น
ที่ไม่แตะ VIP เลย สร้างขึ้นในบทที่ 05 (Cilium) และบทที่ 07 (Gateway)

```
   kubectl / kubelet                      ผู้ใช้เปิด hr.myhr.co.th
         │                                          │
         ▼                                          ▼
   VIP .100:8443                            LB IP .200:443
   keepalived (VRRP) + HAProxy              Cilium LB-IPAM + L2 announcement
   ลอยบน master ตัวใดตัวหนึ่ง                  ประกาศ ARP จาก node ตัวใดตัวหนึ่ง
         │                                          │
         ▼                                          ▼
   apiserver:6443 × 3                       Envoy proxy pod
                                                    │
                                         HTTPRoute → Service → pod
```

| | **VIP `.100`** | **LB IP `.200`** |
|---|---|---|
| ทราฟฟิกอะไร | control plane — `kubectl`, kubelet | ของผู้ใช้จริง |
| ใครถือ IP | keepalived (VRRP) | Cilium L2 announcement |
| กระจายโหลด | HAProxy → apiserver 3 ตัว | eBPF ของ Cilium → Envoy proxy pod |
| เครื่องที่ถืออยู่ตาย | VRRP ย้าย VIP ไป master อื่น | Cilium ย้ายสิทธิ์ตอบ ARP ไป node อื่น |
| ทำที่บทไหน | [03](03-ha-layer.md) | [05](05-cilium.md) + [07](07-gateway-tls.md) |

> 🔴 **HAProxy กับ keepalived ไม่แตะทราฟฟิกของแอปแม้แต่นิดเดียว** — คนที่เปิดเว็บ
> ไม่เคยวิ่งผ่าน `.100` เลย เข้าใจผิดข้อนี้แล้วจะไล่ปัญหาผิดทางทั้งกระบวน
>
> **failure domain แยกกันสนิท:**
> · VIP ล่ม → `kubectl` ใช้ไม่ได้ deploy ไม่ได้ แต่ **pod ที่รันอยู่และผู้ใช้ยังปกติ**
> · L2 announcement ล่ม → ผู้ใช้เข้าไม่ได้ แต่ cluster ข้างในปกติ ยัง `kubectl` ได้
>
> "เข้าเว็บไม่ได้" กับ "kubectl ไม่ได้" แทบไม่เคยมีสาเหตุเดียวกัน

> **เอา Gateway ไปอยู่หลัง VIP เลยไม่ได้เหรอ** — ได้ทางเทคนิค แต่จะบีบทราฟฟิกแอปทั้งหมด
> ผ่าน HAProxy ตัวเดียวบน master เครื่องเดียว ทำให้ master เป็นคอขวดของทั้งระบบ
> และทำลายเหตุผลที่เลือก Cilium LB-IPAM ตั้งแต่แรก

## ก่อนเริ่ม — ต้องมีครบ 7 ข้อ

- [ ] VM 6 เครื่องพร้อม ตาม IP ในตารางด้านล่าง และ **master ทั้ง 3 อยู่คนละ ESXi host** (DRS anti-affinity)
- [ ] **VIP `192.168.50.100` จองแล้ว** และยังไม่มีเครื่องไหนใช้ — ตรวจด้วย `ping -c2 192.168.50.100` ต้องไม่มีคนตอบ
- [ ] ทีม network กัน `192.168.50.200-209` ไว้ให้แล้ว และยืนยันว่า **switch ไม่ได้เปิด Dynamic ARP Inspection** ขวางช่วงนี้
- [ ] **มีเครื่องทดสอบอยู่ในวง `192.168.50.0/24` และไม่ใช่ node ของ cluster** — บทที่ 05 ต้องใช้
      ยืนยัน L2 announcement · ยิงจากโน้ตบุ๊กที่อยู่วงอื่นพิสูจน์อะไรไม่ได้เลย
- [ ] ยืนยันแล้วว่าไม่มี route `10.246.0.0/16` และ `10.247.0.0/16` ในองค์กร
- [ ] เข้า `registry.myhr.co.th` ได้จากทุก node และรู้ว่าเป็น HTTP หรือ HTTPS (ถ้า HTTPS ต้องมีไฟล์ CA)
- [ ] คัดลอก `versions.env` และโฟลเดอร์ `config/` ไปไว้ที่ `/root/k8s/` บนทุกเครื่องแล้ว
      **รันจากเครื่องที่มีrepo (ไม่ใช่บน node)** โดยยืนอยู่ในโฟลเดอร์rootของrepo:

```bash
for ip in 101 102 103 104 105 106; do
  ssh root@192.168.50.$ip 'mkdir -p /root/k8s'
  scp -r docs/versions.env config/ root@192.168.50.$ip:/root/k8s/
done
```

> **บน Windows บล็อกข้างบนใช้ไม่ได้** — มันเป็นไวยากรณ์ของ bash (Git Bash / WSL / เครื่อง Linux)
> ถ้าอยู่ใน PowerShell ให้ใช้อันนี้แทน:

```bash
foreach ($ip in 101..106) {
  ssh root@192.168.50.$ip "mkdir -p /root/k8s"
  scp -r docs/versions.env config "root@192.168.50.${ip}:/root/k8s/"
}
```

> 🔴 **PowerShell 5.1 ไม่มี `&&`** — คำสั่งที่ต่อกันด้วย `&&` (ซึ่งใช้ได้ปกติเมื่อรันบน node)
> จะขึ้น `The token '&&' is not a valid statement separator in this version.`
> ให้แยกเป็นคนละบรรทัด หรือใช้ `;` แทน (ต่างกันตรงที่ `;` รันต่อแม้อันก่อนหน้าจะล้มเหลว)
> · และปลายทางที่มี `$ip` ต้องเขียนเป็น `"...${ip}:/root/k8s/"` ไม่งั้น PowerShell
> จะอ่าน `$ip:` เป็นตัวแปรแบบระบุ scope แล้วพัง

> **ต้องรันซ้ำทุกครั้งที่แก้ไฟล์ในrepo** ไม่ใช่ครั้งเดียวตอนเริ่ม — ไม่งั้นบทที่กำลังทำ
> จะอ้างไฟล์ที่ยังไม่มีบนเครื่อง แล้วเจอ `does not exist` กลางคัน
> ทุกบทมีคำสั่งตรวจไฟล์ของตัวเองอยู่ที่ขั้นที่ 0

## กติกา 6 ข้อของคู่มือชุดนี้

**1 · ทุกเวอร์ชันมาจาก `versions.env` เท่านั้น**
รันบรรทัดนี้ก่อนเริ่มทุก session บนทุกเครื่อง — ถ้าลืม คำสั่งจะ error ทันทีเพราะตัวแปรว่าง
ซึ่งดีกว่าเผลอไปติดตั้งเวอร์ชันผิด

```bash
set -a && source /root/k8s/versions.env && set +a
```

**2 · ทุกคำสั่งมี "ผลลัพธ์ที่ควรเห็น"**
ถ้าผลไม่ตรง **ให้หยุดตรงนั้น** อย่าไปต่อแล้วค่อยกลับมาแก้

**3 · ไม่มีความลับในไฟล์นี้**
password, token และ key ทั้งหมดเป็น placeholder ค่าจริงอยู่ในที่เก็บ secret แยก

**4 · ห้าม `kubectl edit` บน cluster ตรง ๆ**
ทุกอย่างที่ apply ต้องมาจากไฟล์ใน git เพราะเราไม่มี GitOps มาบังคับให้

**5 · ทุกคำสั่ง copy เขียนเป็น `\cp -f` เสมอ — ไม่ใช่ `cp`**
บน Oracle Linux root มี `alias cp='cp -i'` ติดมาจาก `/root/.bashrc` พอ copy ทับไฟล์ที่มีอยู่แล้ว
มันจะถาม `cp: overwrite '...'?` แล้วรอคำตอบ — **ถ้าไม่ได้ตอบ `y` เป๊ะ ๆ มันจะยกเลิกเงียบ ๆ**
ไม่มี error ให้เห็น ของเดิมยังอยู่ที่เดิมทั้งที่คุณคิดว่าทับไปแล้ว
เวลาวางคำสั่งทีละหลายบรรทัด คำถามนี้จะโผล่กลางกอง แล้วมักโดนกด Enter ผ่านไปโดยไม่ทันสังเกต

`\` หน้าคำสั่งบังคับให้ใช้ binary จริงแทน alias — ใส่ `-f` เฉย ๆ ไม่พอ เพราะ `cp -i -f` ยังถามอยู่

**6 · หลังวางไฟล์ config ใช้ `systemctl restart` เสมอ — ไม่ใช่ `enable --now`**
`--now` จะ start ให้**เฉพาะตอนที่ service ยังไม่รัน** ถ้ามันรันอยู่แล้ว คำสั่งจะผ่านไปเงียบ ๆ
โดยไม่โหลด config ใหม่ — คุณจะเห็น `active (running)` แต่มันยังถือไฟล์เก่าอยู่

```bash
systemctl enable <service>     # ให้ขึ้นเองตอน boot
systemctl restart <service>    # โหลด config ที่เพิ่งวาง — ถูกทั้งกรณีรันอยู่และยังไม่รัน
```

## ความจริงสองข้อที่ส่งผลกับทุกอย่างหลังจากนี้

**ไม่มี Ksplice** — ใช้ Oracle Linux แบบฟรี จึงปะ kernel โดยไม่ reboot ไม่ได้
แปลว่าต้อง drain ทุก node ทุก 1-2 เดือน ผลคือ **ทุก Deployment ต้องมี PodDisruptionBudget
และ replica ≥ 2** ไม่ใช่ข้อแนะนำแต่เป็นข้อบังคับ

**Cilium ถือ 3 หน้าที่พร้อมกัน** — CNI + kube-proxy + LB-IPAM ทำให้ชิ้นส่วนน้อยลงมาก
แต่แลกมาด้วยว่า Cilium มีปัญหาทีเดียว pod network, Service และ LoadBalancer ดับพร้อมกัน
และ **ไม่มี kube-proxy ให้ถอยกลับไปใช้** เพราะไม่ได้ติดตั้งไว้เลย

## capacity ที่ใช้ได้จริง

worker รวมกันได้ 48 vCPU / 144 GB **แต่วางแผนได้แค่ 32 vCPU / 96 GB**
เพราะเวลา drain หนึ่งเครื่องจะเหลือ worker ทำงาน 2 ตัว

ผลรวมของ `requests` ทุก pod ต้องไม่เกินตัวเลขนี้ ไม่งั้นวันที่ patch kernel
จะมี pod ค้าง `Pending` และ drain ไม่จบ
