Service (ClusterIP)ชื่อกลางของกลุ่ม pod ใช้ได้เฉพาะภายในคลัสเตอร์ · ทุก service ของเราเป็นแบบนี้ ไม่กิน IP ของ LAN
Service (LoadBalancer)ขอ IP จริงจาก LAN มา 1 ตัว · เราใช้แค่ตัวเดียวคือของ Gateway — ห้ามสร้างเพิ่มรายบริการ
Ciliumตัวจัดการเครือข่ายทั้งหมด ทำ 3 หน้าที่พร้อมกัน: ให้ IP กับ pod · ทำให้ Service ใช้ได้ (แทน kube-proxy) · จ่าย IP ให้ LoadBalancer
LB-IPAM + L2 announcementส่วนของ Cilium ที่หยิบ IP จากช่วง .200-.209 มาให้ แล้วประกาศบน LAN ว่า “IP นี้อยู่ที่ worker เครื่องนี้” ด้วยการตอบ ARP
ARPวิธีที่เครื่องในวงเดียวกันถามหาว่า “IP นี้อยู่ที่การ์ดเน็ตใบไหน” · ถ้า switch บล็อก จะเห็น IP ปกติทุกอย่างแต่เข้าไม่ถึงจริง (ข้อ 08)
NetworkPolicyกฎว่า pod ไหนคุยกับใครได้ · ไม่ใช่ระบบยืนยันตัวตน — มันบอกได้แค่ว่า packet มาจากไหน ไม่รู้ว่าคนที่กดคือใคร
SecurityPolicyของ Envoy Gateway · ใช้บังคับ auth ที่ทางเข้า (API key, JWT, OIDC, จำกัด IP) ทำที่นี่ทีเดียวได้ผลกับทุก service
namespaceห้องแยกของเก็บ resource · ของเรามี myhr-prod กับ myhr-uat เป็นห้องของแอป
cert-manager + internal CAตัวออกใบรับรอง TLS ให้อัตโนมัติจาก CA ที่เราตั้งเอง · เครื่องผู้ใช้ต้องลง root CA ก่อนไม่งั้นเจอ cert warning (ข้อ 06)

🔥 กลุ่มที่ 1 — เจอบ่อยมาก

เจอเกือบทุกครั้งที่เพิ่ม service ใหม่ หรือทุกสัปดาห์ในช่วงเปิดใช้
01

curl ได้ 404 ทั้งที่ HTTPRoute ขึ้น Accepted=True

🔥 บ่อยมาก▾
อาการ — kubectl get httproute เขียว Accepted=True ทุกอย่างดูปกติ แต่ curl กลับได้ HTTP/1.1 404 Not Found และใน response header มี server: envoy

สิ่งที่คนเข้าใจผิด: Accepted=True แปลว่า “Gateway ยอมรับ route นี้เข้ามา” ไม่ได้แปลว่า “มี hostname หรือ path ที่ตรงกับที่คุณกำลังเรียก” ส่วน server: envoy คือหลักฐานว่า request ถึงตัว Envoy แล้ว — ปัญหาอยู่ที่ชั้น route ล้วน ๆ

สาเหตุเรียงตามที่เจอจริง

  1. ผูกผิด listener — route ตั้ง sectionName: https แต่ทดสอบด้วย http:// เจอบ่อยที่สุดในกลุ่มนี้ เพราะตอนทดสอบทุกคนเริ่มที่ HTTP ก่อน
  2. hostname ไม่อยู่ใต้ listener — listener เป็น *.myhr.co.th แต่ route ใส่ hr.myhr.local หรือ myhr.co.th (ไม่มี label หน้า) → ส่วนที่ซ้อนกันเป็นค่าว่าง route เลยไม่รับ traffic ใด ๆ ทั้งที่ยัง Accepted=True
  3. path ไม่ตรง — PathPrefix: /api แต่ curl ไปที่ /
  4. curl ไม่ได้ส่ง Host — ยิงไป IP ตรง ๆ โดยไม่มี -H 'Host: ...' listener ทั้งคู่ผูก hostname ไว้ จึงไม่มี default ให้ตก

วินิจฉัย

NS=demo; RT=echo-route

# 1. อ่านข้อความ status จริง ไม่ใช่ดูแค่คอลัมน์เขียว
kubectl -n $NS get httproute $RT -o jsonpath='{range .status.parents[*]}{.controllerName}{" | "}{range .conditions[*]}{.type}={.status} {.reason}: {.message}{"\n"}{end}{end}'

# 2. listener ไหนมี route เกาะอยู่กี่ตัว — ตัวเลข 0 คือคำตอบ
kubectl -n envoy-gateway-system get gateway myhr-gateway \
  -o jsonpath='{range .status.listeners[*]}{.name}{"  attachedRoutes="}{.attachedRoutes}{"\n"}{end}'

# 3. เทียบ hostname/section/path ของ route กับ listener
kubectl -n $NS get httproute $RT -o jsonpath='{.spec.hostnames}{"\n"}{.spec.parentRefs}{"\n"}'
kubectl -n envoy-gateway-system get gateway myhr-gateway \
  -o jsonpath='{range .spec.listeners[*]}{.name}{" "}{.protocol}{" "}{.hostname}{"\n"}{end}'

02

503 / no healthy upstream — route ถูกแล้วแต่ backend ใช้ไม่ได้

🔥 บ่อยมาก▾
อาการ — ได้ 503 Service Unavailable พร้อมข้อความ no healthy upstream หรือ upstream connect error จาก Envoy

ต่างจากข้อ 01 ตรงที่ Envoy หา route เจอแล้ว — มันรู้ว่าต้องส่งไปที่ Service ไหน แต่ปลายทางไม่มีตัวที่ส่งได้ ปัญหาอยู่ฝั่ง backend เกือบทุกครั้ง ไม่ใช่ฝั่ง Gateway

สาเหตุเรียงตามที่เจอจริง

  1. Service ไม่มี endpoint — selector ไม่ตรง label ของ pod หรือยังไม่มี pod ที่ Ready
  2. port ใน HTTPRoute ไม่ใช่ port ของ Service — ต้องใส่ port ของ Service ไม่ใช่ containerPort
  3. pod ยัง Running แต่ readinessProbe ยังไม่ผ่าน — Spring Boot ตอน cold start เจอประจำ
  4. backend อยู่คนละ namespace โดยไม่มี ReferenceGrant → ดูข้อ 04
  5. NetworkPolicy ปิดทาง Envoy → backend → ดูข้อ 09 (ถ้าทำบทที่ 10 แล้ว ให้สงสัยข้อนี้ก่อน)

วินิจฉัย

NS=demo; SVC=echo

# 1. มี endpoint จริงไหม — ว่างเปล่าคือคำตอบ ไม่ต้องไล่ต่อ
kubectl -n $NS get endpointslice -l kubernetes.io/service-name=$SVC \
  -o jsonpath='{range .items[*]}{range .endpoints[*]}{.addresses[0]}{" ready="}{.conditions.ready}{"\n"}{end}{end}'

# 2. port ของ Service กับที่เขียนใน HTTPRoute ตรงกันไหม
kubectl -n $NS get svc $SVC -o jsonpath='{range .spec.ports[*]}port={.port} targetPort={.targetPort}{"\n"}{end}'
kubectl -n $NS get httproute -o jsonpath='{range .items[*].spec.rules[*].backendRefs[*]}{.name}:{.port}{"\n"}{end}'

# 3. status ของ route ฝั่ง backend — EG จะฟ้องตรงนี้ถ้าอ้าง backend ไม่ได้
kubectl -n $NS get httproute -o jsonpath='{range .items[*]}{range .status.parents[*].conditions[*]}{.type}={.status} {.reason}{"\n"}{end}{end}'

# 4. ยิงตรงเข้า Service จากในคลัสเตอร์ ตัด Envoy ออกจากสมการ
kubectl -n $NS run t --rm -it --image=nicolaka/netshoot --restart=Never -- \
  curl -sS -m5 -o /dev/null -w 'direct=%{http_code}\n' http://$SVC.$NS.svc:80
bash

ยิงตรงก็ไม่ผ่าน → ปัญหาอยู่ที่ตัว service เอง อย่าไปแก้ที่ Gateway

03

HTTPRoute ไม่ถูกผูกกับ Gateway — NotAllowedByListeners / NoMatchingParent

🔥 บ่อยมาก▾
อาการ — kubectl get httproute คอลัมน์ PARENTS ว่าง หรือ Accepted=False พร้อม reason NotAllowedByListeners, NoMatchingParent, NoMatchingListenerHostname

สาเหตุเรียงตามที่เจอจริง

  1. ลืมใส่ namespace ใน parentRefs — Gateway ของเราอยู่ที่ envoy-gateway-system ส่วน route อยู่ที่ namespace ของแอป ถ้าไม่ระบุ Gateway API จะหาใน namespace เดียวกับ route แล้วไม่เจอ
  2. สะกดชื่อ Gateway หรือ sectionName ผิด — ผิดตัวอักษรเดียวก็ได้ NoMatchingParent
  3. Gateway ปิดรับจาก namespace นั้น — ถ้ามีคนเปลี่ยน allowedRoutes.namespaces จาก All เป็น Selector แล้ว namespace ใหม่ยังไม่ได้ติด label
  4. hostname ไม่ซ้อนกับ listener เลย → NoMatchingListenerHostname

🟠 บ่อย▾

สาเหตุคือ timeout ที่ตั้งไว้เพื่อ request แบบธรรมดา ไปมีผลกับ connection ที่ตั้งใจให้เปิดค้าง — ยิ่งถ้าเพิ่งแก้ข้อ 11 โดยตั้ง request: 120s ให้ทุก route ก็จะเจอทันทีว่า stream หลุดทุก 2 นาที

แก้ — แยก route ของ stream ออกมาต่างหาก

  rules:
    # path ปกติ — timeout สั้นตามเดิม
    - matches: [{path: {type: PathPrefix, value: /api}}]
      backendRefs: [{name: hr, port: 80}]
      timeouts: {request: 30s}

    # path ของ stream — ไม่ตัดด้วย request timeout
    - matches: [{path: {type: PathPrefix, value: /events}}]
      backendRefs: [{name: hr, port: 80}]
      timeouts: {request: 0s}     # 0 = ไม่จำกัด
yaml

ถ้ายังหลุดอยู่หลังแก้ตรงนี้ ให้ไล่ต่อทีละชั้น — มีคนตัด connection ได้หลายจุด:

  1. idle timeout ระดับ connection ของ Envoy (ตั้งผ่าน BackendTrafficPolicy)
  2. ตัวแอปเอง (Spring server.servlet.session, Tomcat idle)
  3. firewall/NAT ระหว่างทางที่ตัด idle TCP session — สังเกตได้จากที่มันหลุด เฉพาะตอนไม่มีข้อมูลไหล แต่ไม่หลุดถ้ามี heartbeat

ทางแก้ที่ทนที่สุดไม่ใช่การไล่ยืด timeout ทุกชั้น แต่คือให้ฝั่งแอปส่ง heartbeat/ping ทุก ๆ 20-30 วินาที แล้วทุกชั้นระหว่างทางจะไม่มองว่า connection นี้ idle เลย

  2. ARP cache ค้าง ที่ client หรือที่ switch — IP ยังชี้ MAC เดิมจนกว่าจะหมดอายุ
  3. externalTrafficPolicy: Local — node ที่ประกาศ IP ต้องมี Envoy pod อยู่บนตัวเองด้วย ไม่งั้น traffic จะตกหาย ตรวจค่าจริงก่อนสรุป

  • ทำให้ Envoy proxy มี อย่างน้อย 2 replica และกระจายคนละ node (ตั้งผ่าน EnvoyProxy ที่ผูกกับ GatewayClass) — ข้อนี้สำคัญกว่าทุกข้อ เพราะเราต้อง drain node ทุก 1-2 เดือนอยู่แล้ว

🔵 หายากแต่หนัก▾
อาการ — traffic ของ service หนึ่งไปโผล่ที่อีก service หนึ่ง หรือสลับไปมาโดยไม่มีใครแก้อะไร

Gateway ของเราตั้ง allowedRoutes.namespaces.from: All ไว้ตอนเริ่ม ซึ่งแปลว่า ใครก็ตามที่สร้าง HTTPRoute ได้ จะประกาศ hostname ทับกันได้ Gateway API มีกติกาตัดสินของมันเอง (route ที่สร้างก่อนชนะ ถ้า match specificity เท่ากัน) — ผลลัพธ์จึงขึ้นกับลำดับการสร้าง ไม่ใช่ความตั้งใจของใคร

วินิจฉัย

kubectl get httproute -A -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name}: {range .status.parents[*].conditions[*]}{.type}={.status}({.reason}) {end}{"\n"}{end}'

เลือกวิธี authentication ที่ทางเข้า — และตัดสินว่าทำที่ Gateway หรือที่แอป

🔥 ใช้บ่อยมาก▾
โจทย์ — ก่อนเปิด service ตัวแรกออกไป ต้องตอบให้ได้ว่า “ใครเรียกได้บ้าง และพิสูจน์ตัวตนยังไง” · คำตอบว่า “อยู่ในวง LAN เดียวกัน” ไม่ใช่ authentication — NetworkPolicy บอกได้แค่ว่า packet มาจากไหน ไม่ได้บอกว่าคนที่กดคือใคร

เส้นแบ่งที่ควรยึด

  • Gateway รับผิดชอบ “คุณเป็นใคร” — ตรวจ key/token/cert ให้จบตรงนี้ แล้วทุก service ได้ผลเหมือนกันฟรี ไม่ต้องเขียนซ้ำทุกตัว และไม่มี service ไหนลืม
  • แอปรับผิดชอบ “คุณทำอะไรได้” — สิทธิ์ระดับข้อมูล (พนักงานคนนี้ดูเงินเดือนใครได้) Gateway ไม่มีทางรู้ อย่าพยายามยัดลง policy
  • ห้ามให้แอปเชื่อ header ที่ใครก็ส่งเข้ามาได้ — ถ้า Gateway ใส่ x-user-email ให้แอป ต้องมั่นใจว่า Envoy ลบ header เดิมที่ client ส่งมาทิ้งก่อน ไม่งั้นใครก็ปลอมเป็นใครก็ได้ด้วย curl -H บรรทัดเดียว

ข้อสุดท้ายคือช่องโหว่คลาสสิกของการย้าย auth มาไว้ที่ gateway และเป็นข้อที่ต้องทดสอบด้วยการลองปลอมจริง ๆ ไม่ใช่แค่อ่าน config

🔥 ใช้บ่อยมาก▾
โจทย์ — ระบบอื่นในองค์กร (payroll, ERP, job กลางคืน) ต้องเรียก API ของเรา ไม่มีคนกดหน้าจอ จึงใช้ login ไม่ได้ · ต้องการอะไรที่ตั้งได้เร็ว หมุนได้ และแยกได้ว่าใครเป็นใคร

apiVersion: gateway.envoyproxy.io/v1alpha1
kind: SecurityPolicy
metadata:
  name: hr-api-keys

      - name: hr-api-keys           # Secret ที่เก็บ key ของแต่ละผู้เรียก
    extractFrom:
      - headers: ["x-api-key"]      # header เท่านั้น — ห้าม query (อ่านเหตุผลข้างล่าง)
yaml
# 1 key = 1 ผู้เรียก ตั้งชื่อ key ให้รู้ว่าใคร จะได้เพิกถอนทีละรายได้
kubectl -n myhr-prod create secret generic hr-api-keys \

  --from-literal=erp-nightly-job="$(openssl rand -hex 32)"

🔴 ห้ามรับ key ทาง query string เด็ดขาด

?api_key=xxx จะถูกเขียนลง access log ของ Envoy และ log ของแอป แล้วไหลต่อไปเก็บใน Loki ตามที่ตั้งไว้ใน P11 — กลายเป็นว่า credential ทุกตัวถูกเก็บเป็น plaintext ในระบบ log ที่คนเข้าถึงได้กว้างกว่า และย้อนกลับไปลบไม่ได้ · ข้อนี้เป็นสิ่งที่ผู้ตรวจจะถามตรง ๆ

การหมุน key ที่ไม่ทำให้ระบบปลายทางดับ

  1. เพิ่ม key ใหม่เข้า Secret โดยยังไม่ลบตัวเก่า — ช่วงนี้ใช้ได้ทั้งสองตัว
  2. แจ้งเจ้าของระบบปลายทางให้เปลี่ยนไปใช้ตัวใหม่ ตั้ง deadline ชัดเจน
  3. ยืนยันจาก log ว่าไม่มีใครใช้ key เก่าแล้วจริง ๆ ก่อนลบ ไม่ใช่เดาจากที่เขาบอก
  4. ลบ key เก่าออกจาก Secret

ถ้าทำข้อ 3 ไม่ได้เพราะแยกไม่ออกว่าใครใช้ key ไหน แปลว่าตอนตั้งใช้ key เดียวร่วมกัน หลายระบบ — ซึ่งคือเหตุผลที่ต้อง 1 key ต่อ 1 ผู้เรียก ตั้งแต่วันแรก key ร่วมเพิกถอนไม่ได้เลยโดยไม่ทำใครสักคนพัง

🔥 ใช้บ่อยมาก▾

jwtoidc

Gateway ทำอะไรตรวจลายเซ็น + issuer + audience แล้วปล่อยผ่านจัดการ redirect · แลก code · ตั้ง cookie · แล้วค่อยปล่อยผ่าน

ตรวจ JWT ที่ Gateway แล้วส่ง claim ต่อให้แอป

apiVersion: gateway.envoyproxy.io/v1alpha1
kind: SecurityPolicy
metadata:
  name: hr-jwt
  namespace: myhr-prod
spec:
  targetRefs:
    - group: gateway.networking.k8s.io
      kind: HTTPRoute
      name: hr-api
  jwt:
    providers:
      - name: myhr-idp
        issuer: "https://idp.myhr.co.th/realms/myhr"
        audiences: ["myhr-hr-api"]         # ระบุเสมอ — ไม่งั้น token ของ service อื่นก็ใช้ได้
        remoteJWKS:
          uri: "https://idp.myhr.co.th/realms/myhr/protocol/openid-connect/certs"
        claimToHeaders:                    # ส่ง claim ต่อให้แอปใช้ ไม่ต้อง decode เอง
          - claim: email
            header: x-user-email
          - claim: sub
            header: x-user-id
yaml

🔴 สามข้อที่ทำให้พังแบบหาสาเหตุไม่เจอ

  1. Envoy ต้องออกไปดึง JWKS ได้ — ถ้าวันหนึ่งมี default-deny ครอบ envoy-gateway-system ด้วย หรือ DNS ของ IdP resolve ไม่ได้ ทุก request จะกลายเป็น 401 พร้อมกันทั้งระบบ โดยที่ token ของผู้ใช้ไม่ได้ผิดอะไรเลย — ให้เตรียม policy egress ไป IdP ไว้คู่กับ policy นี้เสมอ (ดู P13)
  2. เวลาเพี้ยน = token “ยังไม่ถึงเวลาใช้” หรือ “หมดอายุแล้ว” ทั้งที่เพิ่งออกมา — ต้องมี NTP ตรงกันทุก node (ข้อเดียวกับที่ P11 ต้องการ)
  3. ลบ header ปลอมจาก client ก่อนเสมอ — ถ้าแอปเชื่อ x-user-email แต่ Envoy ไม่ได้ลบตัวที่ client ส่งมาเอง ใครก็เป็น HR ได้ด้วย curl -H
# ต้องได้ 401 — ถ้าได้ 200 แปลว่าแอปเชื่อ header ที่ client ปลอมมา
curl -sS -o /dev/null -w 'ปลอม header = %{http_code}\n' \
  --cacert /root/k8s/myhr-root-ca.crt --resolve "hr-api.myhr.co.th:443:${GW_IP}" \
  -H 'x-user-email: ceo@myhr.co.th' https://hr-api.myhr.co.th/api/employees
bash

ตั้งชื่อ host + ขอ DNS + ขอ cert ให้จบครั้งเดียว

🟠 ตั้งครั้งเดียว▾
โจทย์ — ไม่อยากต้องเปิด ticket หาทีม network ทุกครั้งที่มี service ใหม่ และไม่อยากออก cert ใหม่ทุกครั้งเช่นกัน

ขอครั้งเดียว: wildcard record หนึ่งอัน

*.myhr.co.th.    IN A    192.168.50.200
text

หลังจากนี้ service ใหม่ทุกตัวแค่เขียน hostnames: ใน HTTPRoute ก็ใช้งานได้ทันที ไม่ต้องคุยกับใคร — ซึ่งคือทั้งหมดที่ต้องการจากการเลือก Gateway API

ข้อจำกัดของ wildcard ที่ต้องรู้ก่อนตั้งชื่อ

*.myhr.co.th ครอบแค่ระดับเดียว — hr.myhr.co.th ผ่าน แต่ api.hr.myhr.co.th ไม่ผ่าน ทั้งฝั่ง DNS และฝั่ง cert ถ้าออกแบบชื่อเป็นสองระดับตั้งแต่แรกจะต้องขอ record และ cert เพิ่มทุกโซน

✅ hr.myhr.co.th          hr-api.myhr.co.th        hr-uat.myhr.co.th
❌ api.hr.myhr.co.th      uat.hr.myhr.co.th
text

โจทย์ — ค่า default ของ Envoy ออกแบบมาให้ปลอดภัยกับ Envoy ไม่ได้ออกแบบมาให้เหมาะกับแอปของเรา ถ้าไม่ตั้งอะไรเลยจะเจอทั้ง 504 ที่ไม่ควรเกิด และ connection ค้างสะสมที่ไม่ควรค้าง

1 · timeout — ตั้งทุก route เสมอ อย่าปล่อยว่าง

แม่แบบตั้ง 30s ไว้ให้แล้ว · path ที่รู้ว่าช้าจริงค่อยตั้งยาวเป็นราย rule (ดูข้อ 11) · path ที่เป็น stream ตั้ง 0s (ดูข้อ 13) อย่าตั้งยาวทั้งระบบ เพราะ timeout ยาว = connection ค้างสะสมตอน backend ป่วย แล้วลามจนล่มทั้ง Gateway

2 · retry — เฉพาะที่ยิงซ้ำแล้วไม่เกิดผลข้างเคียง

GET ยิงซ้ำได้ · POST ที่สร้างรายการเงินเดือนยิงซ้ำไม่ได้ retry ที่ตั้งกว้าง ๆ ทั้ง Gateway คือวิธีสร้างรายการซ้ำโดยไม่มีใครรู้ตัว — และจะไปโผล่เป็นปัญหาทางบัญชีทีหลัง ไม่ใช่ปัญหาทาง IT

ถ้าจะเปิด retry ให้เปิดเป็นราย route ที่เป็น read-only เท่านั้น และเขียนกำกับไว้ว่าทำไม route นั้นปลอดภัย

3 · rate limit — ที่ endpoint ที่แพงหรืออ่อนไหว

login, export รายงาน, endpoint ค้นหาที่ยิง DB หนัก — สามอย่างนี้ควรมีเพดาน ไม่ใช่เพื่อกันคนนอก (ระบบอยู่ในวงภายใน) แต่เพื่อกันสคริปต์ของเราเองที่ยิงพลาด แล้วทำ DB นอก cluster ล่มไปด้วย

🟠 ตั้งครั้งเดียว▾
โจทย์ — เว็บที่เปิดให้พนักงานใช้ ถ้าไม่มี header พวกนี้ จะถูกรายงานเป็นช่องโหว่ทันทีเวลามีการสแกน · และเป็นของที่ไม่ควรให้แต่ละทีมไปทำเอง เพราะจะได้ไม่เท่ากันและมีคนลืม

header ที่ควรมี และมันกันอะไร

headerกันอะไร (แบบเข้าใจง่าย)
Strict-Transport-Securityบังคับให้เบราว์เซอร์จำว่า “เว็บนี้ต้อง https เท่านั้น” — กันการถูกหลอกให้กลับไปใช้ http
X-Content-Type-Options: nosniffห้ามเบราว์เซอร์เดาชนิดไฟล์เอง — กันไฟล์ที่ผู้ใช้อัปโหลดถูกรันเป็นสคริปต์
X-Frame-Options: DENYห้ามเว็บอื่นเอาหน้าเราไปฝังใน iframe แล้วหลอกให้กดผิด
Referrer-Policyไม่ให้ URL ภายในของเราหลุดไปกับ request ที่ออกไปเว็บนอก
Content-Security-Policyคุมว่าหน้าเว็บโหลดสคริปต์จากที่ไหนได้บ้าง — แรงที่สุดแต่ต้องคุยกับทีม frontend ก่อน ตั้งมั่วแล้วหน้าเว็บพังทั้งหน้า

              - name: X-Content-Type-Options
                value: "nosniff"
              - name: X-Frame-Options
                value: "DENY"
              - name: Referrer-Policy
                value: "strict-origin-when-cross-origin"
      backendRefs: [{name: hr-web, port: 80}]
