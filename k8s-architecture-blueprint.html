ขอบเขตและหลักการออกแบบ

เอกสารชุดใหม่ไม่ใช่แค่การอัปเดตเลขเวอร์ชันจากของเดิม แต่เป็นการเขียนใหม่โดยเพิ่มสิ่งที่ของเดิมไม่มีเลย — โดยเฉพาะ day-2 operations (backup / upgrade / cert renewal) ซึ่งเป็นสาเหตุที่ทำให้ cluster เดิมเดินต่อไม่ได้และต้องมาตั้งใหม่ทั้งชุดในรอบนี้

หลักการความหมายในทางปฏิบัติ
Reproducibleทุกเวอร์ชันถูก pin ไว้ในไฟล์เดียว (versions.env) ไม่มีคำว่า “latest” ในคู่มือ คนอ่านคนละเดือนต้องได้ cluster เหมือนกัน
ไม่มีความลับในเอกสารทุก password / token / key เป็น placeholder ล้วน ค่าจริงอยู่ในที่เก็บ secret แยก คู่มือชุดเดิมมี root password และ cluster-admin token ฝังอยู่ในไฟล์ ต้องไม่เกิดซ้ำ
ทุกขั้นตอนมี verifyแต่ละคำสั่งตามด้วย “ผลลัพธ์ที่ควรเห็น” — ของเดิมมีแต่คำสั่ง คนทำตามไม่รู้ว่าพลาดตอนไหนจนไปพังทีหลัง
แยก “ทำอะไร” จาก “ทำไม”ตัวคู่มือเป็น runbook สั้น ตรงไปตรงมา ส่วนเหตุผล/ทางเลือกอยู่ในเอกสารสถาปัตยกรรม (ฉบับนี้) คนทำงานตอนตีสองไม่ต้องอ่านเหตุผล
Upgrade เป็นพลเมืองชั้นหนึ่งKubernetes ออก 3 minor/ปี และ support ~1 ปี แปลว่า ต้อง upgrade อย่างน้อยปีละครั้ง คู่มือต้องรองรับเรื่องนี้ ไม่ใช่คู่มือ “ติดตั้งครั้งเดียวจบ”
ข้อสมมติที่ยังต้องยืนยัน

ผมสมมติจากเอกสารเดิมว่า: node เป็น VM บน VMware (interface ชื่อ ens192), OS เป็นตระกูล RHEL (ใช้ yum + firewalld + SELinux), มี private registry ที่ registry.myhr.co.th, และ workload หลักเป็น Spring Boot microservices ถ้าข้อไหนไม่ตรง บอกได้ครับ จะมีผลกับ L00, L02 และ L07 โดยตรง

L01

OS Baseline

kernel modules · sysctl · swap · SELinux · firewalld

หน้าที่

ปรับ kernel ให้ทำ container networking ได้ และเปิดพอร์ตที่ component ต้องใช้ ชั้นนี้ดูน่าเบื่อแต่เป็นต้นเหตุของ “pod ข้าม node ไม่ได้” เกือบทุกเคส

รายการที่ต้องมี

รายการหน้าที่สถานะในคู่มือเดิม
modprobe overlayoverlayfs สำหรับ container filesystemไม่มี
modprobe br_netfilterให้ traffic ที่ผ่าน bridge ถูก iptables/nftables เห็นไม่มี — และ sysctl ด้านล่างจะ set ไม่ติดถ้าไม่โหลด module นี้ก่อน
/etc/modules-load.d/k8s.confให้ทั้งสองโหลดอัตโนมัติหลัง rebootไม่มี — reboot แล้วพัง
net.ipv4.ip_forward=1routing ระหว่าง podมี
net.bridge.bridge-nf-call-iptables=1Service/NetworkPolicy ทำงานกับ pod ที่ต่อผ่าน bridgeมี แต่ set ไม่ติด
net.bridge.bridge-nf-call-ip6tables=1เช่นเดียวกันฝั่ง IPv6ไม่มี
ปิด swapkubelet คำนวณ memory pressure จากสมมติฐานว่าไม่มี swapมี — NodeSwap มีแล้วแต่ยังเป็น beta แนะนำปิดต่อ
SELinux permissiveเลี่ยง denial ตอน container เขียน volumeมี — เป็นแนวทางมาตรฐานของ kubeadm แต่คู่มือควรระบุชัดว่าเป็นการยอมรับความเสี่ยง ไม่ใช่ best practice

L02

Container Runtime

containerd · runc · CNI binaries · cgroup driver

ใครทำอะไร

ตัวหน้าที่
containerdรับคำสั่งจาก kubelet ผ่าน CRI socket จัดการ image, snapshot, lifecycle ของ container
runcตัวที่สร้าง namespace/cgroup จริง ๆ ตามมาตรฐาน OCI — containerd เรียกใช้อีกที
CNI plugin binariesไฟล์ executable ใน /opt/cni/bin ที่ทำหน้าที่ต่อ network ให้ pod แต่ละตัว คนละเรื่องกับ CNI ที่ L05 — ตัวนั้นคือ controller ที่เรียกใช้ binaries เหล่านี้
crictlเครื่องมือ debug ระดับ CRI ใช้ตอน pod ไม่ยอมขึ้นและ kubectl ยังไม่มีข้อมูล

ตัวเลือก

ตัวเลือกข้อดีข้อเสีย
containerd 2.2 จาก tarball แนะนำคุมเวอร์ชันได้เป๊ะ (ตรงหลัก reproducible), ตรงกับที่ทีมทำอยู่แล้ว, ไม่ผูกกับ repo ของ distroต้องอัปเดตเองด้วยมือ ไม่มี dnf update ให้
containerd จาก repo ของ distroอัปเดตตาม OS อัตโนมัติเวอร์ชันตามหลัง และอาจถูกอัปเดตโดยไม่ตั้งใจ ทำให้ node สองเครื่องไม่เหมือนกัน
CRI-Oผูกเวอร์ชันกับ Kubernetes 1:1 ทำให้เลือกเวอร์ชันง่าย, ออกแบบมาเพื่อ k8s อย่างเดียวทีมไม่คุ้น, เอกสาร community น้อยกว่า, ต้องเรียนใหม่หมด

สิ่งที่คู่มือใหม่ต้องมีเพิ่ม

  • สร้าง /etc/containerd/config.toml จาก containerd config default — คู่มือเดิมข้ามขั้นนี้ไปเลย
  • ตั้ง SystemdCgroup = true ให้ตรงกับ kubelet ถ้าไม่ตรง node จะดูปกติแต่ evict pod มั่วตอนโหลดสูง
  • containerd 2.x ใช้ config version 3 และ key เปลี่ยนเป็น io.containerd.cri.v1.runtime (เดิม io.containerd.grpc.v1.cri)
  • sandbox image ต้องตรงกับที่ kubeadm คาด — ตรวจด้วย kubeadm config images list
  • /etc/containerd/certs.d/registry.myhr.co.th/hosts.toml สำหรับ private registry — ถ้า cert เป็น self-signed หรือ registry เป็น HTTP ต้องประกาศตรงนี้ ไม่งั้น pull ไม่ได้ (ดู L08)
  • ขั้นตอน verify: crictl info | grep -i cgroup และ pull image ทดสอบจาก registry จริง
ช่องว่างที่ใหญ่ที่สุดในชั้นนี้

cluster เดิมรันโดยไม่มี config.toml เลย แปลว่า containerd ใช้ค่า default ซึ่งเป็น cgroupfs ขณะที่ kubelet ถูกตั้งเป็น systemd — เป็น mismatch ที่เอกสาร Kubernetes เตือนไว้ชัดเจนว่าทำให้ node ไม่เสถียรภายใต้แรงกดดันด้าน resource

หน้าที่

หน้าที่

MTU — เรื่องที่ลืมกันบ่อยที่สุด

VXLAN ห่อ packet เพิ่มอีก 50 bytes ถ้า node MTU = 1500 แล้วปล่อย pod MTU ไว้ที่ 1500 ด้วย จะเจออาการ “ping ผ่าน แต่ HTTP request ใหญ่ ๆ ค้าง” หรือ “TLS handshake ล้มเป็นบางครั้ง” — เป็นอาการที่หลอกให้ไปไล่หาปัญหาที่ application คู่มือใหม่ต้องมีขั้นตอนตั้ง MTU และวิธีทดสอบด้วย ping -M do -s

Calicoรองรับpolicy engine ที่สุกงอมที่สุด, มี BGP mode ทำ routing จริงได้, แนวคิดยังใกล้ Flannelชิ้นส่วนเพิ่มขึ้นปานกลาง เรียนรู้ไม่นาน

เหตุผลที่เสนอ Cilium

ระบบนี้เก็บข้อมูลส่วนบุคคลของพนักงาน ซึ่งทำให้ NetworkPolicy แบบ default-deny กลายเป็นข้อกำหนด ไม่ใช่ของเล่น — Flannel ทำไม่ได้เลย ต้องเปลี่ยนอยู่ดี และเมื่อจะเปลี่ยน Cilium ให้ของแถมที่แก้ปัญหาอื่นในเอกสารนี้ไปพร้อมกัน: แทน kube-proxy ได้ (ตัดประเด็น D5 ทิ้ง), มี Gateway API ในตัว (ช่วย L06), และ Hubble ทำให้ตอบคำถาม “pod นี้คุยกับใครบ้าง” ได้ ซึ่งเป็นคำถามที่ต้องตอบเวลา audit

ทางสายกลาง: ถ้าประเมินว่าความชันของ Cilium เสี่ยงเกินสำหรับรอบนี้ ให้เลือก Calico — ได้ NetworkPolicy ครบ โดยที่แนวคิดยังใกล้ของเดิมพอที่ทีมจะ debug ได้ในคืนแรกที่มีปัญหา

หน้าที่

CSI driver คือสะพานระหว่าง Kubernetes กับระบบเก็บข้อมูลจริง StorageClass คือ “เมนู” ที่บอกว่ามีที่เก็บแบบไหนให้เลือกบ้าง เมื่อ pod ขอ PVC ระบบจะสร้าง PV ให้อัตโนมัติตามเมนูนั้น

ตัวเลือก

ตัวเลือกเหมาะกับข้อควรระวัง
ไม่มีเลย ของเดิมถ้า workload เป็น stateless ล้วน ฐานข้อมูลอยู่นอก clusterต้องประกาศให้ชัดในคู่มือ ไม่ใช่ปล่อยให้เป็นความบังเอิญ — วันหนึ่งจะมีคนอยากลง Redis แล้วติด
vSphere CSI ถ้าอยู่บน VMwareใช้ datastore เดิมที่มีอยู่ ไม่ต้องซื้อของใหม่ต้องได้สิทธิ์ vCenter และต้องดูแลเวอร์ชันให้เข้ากับ vSphere
NFS CSI driverต้องการ RWX (หลาย pod เขียนพร้อมกัน) เช่นที่เก็บไฟล์แนบNFS server กลายเป็น single point of failure และ latency สูงกว่า block
local-path-provisionerต้องการความเร็ว ยอมให้ข้อมูลผูกกับ nodepod ย้าย node ไม่ได้ ต้องมี backup ระดับ application เอง
Longhornอยากได้ replicated block storage ในตัว cluster พร้อม snapshotกิน CPU/RAM/disk ของ worker และเพิ่มสิ่งที่ต้องดูแลอีกระบบหนึ่ง
คำแนะนำ

เคาะ D8 ให้ชัดก่อน ถ้าคำตอบคือ “ฐานข้อมูลอยู่นอก cluster ตลอด” ให้เขียนบทนี้สั้น ๆ ว่า ไม่มี StorageClass โดยเจตนา พร้อมเหตุผล — นั่นคือคำตอบที่ใช้ได้และประหยัดงานมหาศาล ถ้าคำตอบคือ “อาจมี” และอยู่บน VMware ให้ลง vSphere CSI ตั้งแต่แรกจะง่ายกว่ามาไล่ทำทีหลังตอนมีคนรออยู่

Security & Governance

RBAC · Pod Security · NetworkPolicy · secrets · audit

ชั้นนี้ไม่มีอยู่ในคู่มือเดิมเลย

และเป็นชั้นที่สำคัญที่สุดสำหรับระบบที่เก็บข้อมูลส่วนบุคคลของพนักงาน ทุก account ที่ปรากฏในเอกสารเดิมเป็น cluster-admin ทั้งหมด และ deployment ตัวอย่างรันด้วย runAsUser: 0

องค์ประกอบ

ตัวหน้าที่ที่เสนอ
RBACใครทำอะไรได้บ้างสร้าง role ตามหน้าที่จริง: developer (อ่าน + ดู log ใน namespace ตัวเอง), deployer, cluster-ops — cluster-admin สงวนไว้ให้ break-glass เท่านั้น
Pod Security Admissionกันไม่ให้ pod ขอสิทธิ์เกินจำเป็นติด label restricted ทุก namespace ของ application, privileged เฉพาะ namespace ของ CNI/system
NetworkPolicyควบคุมว่า pod ไหนคุยกับ pod ไหนได้default-deny ทุก namespace แล้วค่อยเปิดเฉพาะเส้นทางที่จำเป็น — ต้องใช้ CNI ที่รองรับ (ดู D4)
etcd encryption at restเข้ารหัส Secret ที่เก็บใน etcdตั้ง EncryptionConfiguration ตั้งแต่วัน init — ทำทีหลังต้องไล่ re-encrypt ทุก resource
Secret managementเก็บรหัสของ applicationSecret ของ Kubernetes เป็นแค่ base64 ไม่ใช่การเข้ารหัส — ทางเลือก: Sealed Secrets (ง่าย เก็บใน git ได้) หรือ External Secrets + Vault (ครบกว่า)
Audit logบันทึกว่าใครทำอะไรกับ clusterเปิด audit policy ที่ apiserver ตั้งแต่แรกและส่งเข้า Loki — ถ้าต้องตอบคำถามผู้ตรวจสอบ นี่คือหลักฐานชิ้นเดียวที่มี
ข้อสังเกตเรื่อง PDPA

ระบบ HR เก็บข้อมูลส่วนบุคคลของพนักงาน ซึ่งโดยทั่วไปมาพร้อมข้อกำหนดเรื่องการควบคุมการเข้าถึงและร่องรอยการตรวจสอบ ผมไม่ทราบว่าองค์กรตีความข้อกำหนดไว้อย่างไร แต่รายการในตารางข้างบน (RBAC แยกตามหน้าที่, NetworkPolicy, encryption at rest, audit log) เป็นชุดพื้นฐานที่มักถูกถามหา — ควรให้ฝ่ายที่ดูแลเรื่อง compliance ช่วยยืนยันก่อนเคาะ D4 เพราะถ้าต้องมี NetworkPolicy จริง จะตัดตัวเลือก Flannel ทิ้งทันที

ตัวเลือก — วิธี deploy

ตัวเลือกข้อดีข้อเสีย
kubectl apply มือ ของเดิมง่าย ไม่มีอะไรต้องเรียนไม่มีร่องรอยว่าใคร deploy อะไรเมื่อไหร่, สถานะจริงกับใน git ไม่ตรงกันเรื่อย ๆ, rollback ต้องพึ่งความจำ
Helm chartทำ template ได้ มี rollback ในตัว จัดการ values ต่อ environment ได้ยังต้องมีคนรันคำสั่ง ยังไม่แก้ปัญหา drift
Argo CD แนะนำgit คือแหล่งความจริงเดียว, เห็น drift ทันที, rollback = revert commit, มี UI ที่ให้สิทธิ์ dev ดู deployment ตัวเองได้โดยไม่ต้องให้ kubectlเป็นระบบเพิ่มอีกหนึ่งที่ต้องดูแล และทีมต้องเปลี่ยนนิสัยการทำงาน
Flux CDเบากว่า Argo, เป็น GitOps เหมือนกันไม่มี UI ในตัว ซึ่งเป็นข้อดีของ Argo ที่ทีม dev จะได้ประโยชน์มากที่สุด

มาตรฐาน manifest ที่ควรบังคับ

ดูจาก zeeme-ads/deployment.yml ของเดิมแล้ว มีหลายอย่างที่ควรเป็นแม่แบบใหม่:

รายการของเดิมที่ควรเป็น
ผู้ใช้ที่รันrunAsUser: 0non-root + readOnlyRootFilesystem + drop capabilities ทั้งหมด
resourcesไม่มีตั้ง requests/limits ทุกตัว — ไม่มีแล้ว scheduler ตัดสินใจมั่วและ node ล้มได้
probesไม่มีreadinessProbe + livenessProbe + startupProbe (Spring Boot เริ่มช้า ต้องมีตัวหลัง)
PodDisruptionBudgetไม่มีมีทุก service — ไม่งั้นตอน drain node เพื่อ upgrade จะดับพร้อมกันหมด
anti-affinityไม่มีกระจาย replica ข้าม node ด้วย topologySpreadConstraints
ResourceQuota / LimitRangeไม่มีต่อ namespace กัน namespace เดียวกินทั้ง cluster

Helm 3 หยุด bugfix ไปแล้วเมื่อ ก.ค. 2026 และ security patch จะหยุด ก.พ. 2027 คู่มือใหม่ควรอิง Helm 4 ตั้งแต่แรก แต่ต้องเผื่อเวลาทดสอบ chart เดิม เพราะ Helm 4 เปลี่ยนมาใช้ Server-Side Apply เป็นค่าเริ่มต้นและต้องการสิทธิ์ RBAC เพิ่มสำหรับ kstatus

Day-2 Operations

backup · cert renewal · upgrade · DR

นี่คือชั้นที่ทำให้ต้องมาตั้ง cluster ใหม่ในรอบนี้

คู่มือเดิมพา cluster ขึ้นมาได้ แต่ไม่มีบทไหนบอกวิธีทำให้มันอยู่ต่อ ไม่มี backup, ไม่มีการต่ออายุ cert, ไม่มีวิธี upgrade — พอ cert หมดอายุและเวอร์ชัน EOL ทางเดียวที่เหลือคือรื้อทำใหม่ ถ้าเลือกได้แค่บทเดียวที่จะเขียนให้ดีที่สุด ให้เลือกบทนี้

สิ่งที่ต้องมี

งานความถี่รายละเอียด
etcd snapshotทุกวัน + ก่อนแตะอะไรก็ตามetcdctl snapshot save ผ่าน CronJob เก็บออกนอก cluster และต้องมี checksum
ซ้อมกู้จริงทุกไตรมาสbackup ที่ไม่เคยกู้สำเร็จ = ไม่มี backup — ซ้อมบน cluster ทดสอบและบันทึกเวลาที่ใช้จริง
ตรวจอายุ certificateทุกเดือน + alert อัตโนมัติkubeadm certs check-expiration → ถ้าเหลือ < 60 วันให้ kubeadm certs renew all แล้ว restart static pod
Patch upgradeทุก 1-2 เดือนภายใน minor เดียวกัน ทำได้เร็ว ความเสี่ยงต่ำ
Minor upgradeปีละ 1-2 ครั้งห้ามข้าม minor — ต้องไปทีละขั้น (1.36 → 1.37 → 1.38) ลำดับคือ control plane แรกก่อน แล้วที่เหลือ แล้วค่อย worker ทีละตัวพร้อม drain
เพิ่ม/ถอด nodeตามต้องการรวมถึงวิธีออก bootstrap token ใหม่ (ของเก่าหมดอายุใน 24 ชม.) และวิธี drain ให้ปลอดภัย
ทบทวน capacityทุกไตรมาสดู request vs usage จริงจาก Prometheus แล้วปรับ
ก่อนอื่นเลย — ตรวจ cluster เดิมก่อน

ถ้า cluster เดิมยังรันอยู่ ให้รัน kubeadm certs check-expiration บนทุก master ก่อนทำอะไรทั้งสิ้น cert ของ kubeadm มีอายุ 1 ปี และจะต่ออายุอัตโนมัติเมื่อ upgrade เท่านั้น — cluster ที่ตั้งเมื่อ 2-3 ปีก่อนและไม่เคย upgrade มีโอกาสสูงที่ cert หมดอายุไปแล้ว ซึ่งจะเปลี่ยนแผนการย้าย workload ทั้งหมด
