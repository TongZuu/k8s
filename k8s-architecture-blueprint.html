ขอบเขตและหลักการออกแบบ

เอกสารชุดใหม่ไม่ใช่แค่การอัปเดตเลขเวอร์ชันจากของเดิม แต่เป็นการเขียนใหม่โดยเพิ่มสิ่งที่ของเดิมไม่มีเลย — โดยเฉพาะ day-2 operations (backup / upgrade / cert renewal) ซึ่งเป็นสาเหตุที่ทำให้ cluster เดิมเดินต่อไม่ได้และต้องมาตั้งใหม่ทั้งชุดในรอบนี้

หลักการความหมายในทางปฏิบัติ
Reproducibleทุกเวอร์ชันถูก pin ไว้ในไฟล์เดียว (versions.env) ไม่มีคำว่า “latest” ในคู่มือ คนอ่านคนละเดือนต้องได้ cluster เหมือนกัน
ไม่มีความลับในเอกสารทุก password / token / key เป็น placeholder ล้วน ค่าจริงอยู่ในที่เก็บ secret แยก คู่มือชุดเดิมมี root password และ cluster-admin token ฝังอยู่ในไฟล์ ต้องไม่เกิดซ้ำ
ทุกขั้นตอนมี verifyแต่ละคำสั่งตามด้วย “ผลลัพธ์ที่ควรเห็น” — ของเดิมมีแต่คำสั่ง คนทำตามไม่รู้ว่าพลาดตอนไหนจนไปพังทีหลัง
แยก “ทำอะไร” จาก “ทำไม”ตัวคู่มือเป็น runbook สั้น ตรงไปตรงมา ส่วนเหตุผล/ทางเลือกอยู่ในเอกสารสถาปัตยกรรม (ฉบับนี้) คนทำงานตอนตีสองไม่ต้องอ่านเหตุผล
Upgrade เป็นพลเมืองชั้นหนึ่งKubernetes ออก 3 minor/ปี และ support ~1 ปี แปลว่า ต้อง upgrade อย่างน้อยปีละครั้ง คู่มือต้องรองรับเรื่องนี้ ไม่ใช่คู่มือ “ติดตั้งครั้งเดียวจบ”

สิ่งที่ต้องเคาะก่อนลงมือเขียน

ข้อเหล่านี้กำหนดหน้าตาของคู่มือทั้งชุด ถ้าเปลี่ยนทีหลังจะต้องรื้อหลายบท เรียงจากผลกระทบมากไปน้อย

เคาะครบแล้วทั้ง 11 ข้อ

ทุกข้อด้านล่างปิดแล้ว แถวที่ไฮไลต์ในแต่ละตารางคือตัวที่เลือก ส่วนแถวอื่นเก็บไว้เป็นบันทึกเหตุผล — ตอบคำถาม “ทำไมไม่เลือกตัวนั้น” ได้โดยไม่ต้องประชุมใหม่

สรุปทั้งชุด: Kubernetes 1.36.x บน Oracle Linux 9.8 (UEK 8U2) · stacked etcd 3 master · keepalived + HAProxy เป็น systemd · Cilium ทำทั้ง CNI, แทน kube-proxy และจ่าย LoadBalancer IP · Envoy Gateway เป็นทางเข้า · ไม่มี persistent storage · deploy ด้วย kubectl apply

ผลรวมคือ cluster ที่มีชิ้นส่วนน้อยกว่าที่เสนอไว้ตอนแรกพอสมควร — ตัด MetalLB, ตัด CSI, ตัด kube-proxy และตัด Argo CD ออกไปทั้งหมด ซึ่งช่วยลดความเสี่ยง “ขอบเขตบานปลาย” ไปได้มาก

D2 ระบบปฏิบัติการฐาน เคาะแล้ว — Oracle Linux 9.8
ข้อสรุป

ทีมเลือก Oracle Linux 9.8 (ออก มิ.ย. 2026 · binary-compatible กับ RHEL 9.8) เป็น OS ฐานทุก node ทั้ง control plane และ worker แบบไม่ซื้อ support — ดึง package จาก yum.oracle.com ที่เปิดสาธารณะ ตัวเลือกอื่นในตารางเก็บไว้เป็นบันทึกเหตุผลเท่านั้น ไม่ต้องพิจารณาใหม่

“ใช้แบบฟรี” แปลว่าอะไรบ้าง

ยังได้: ตัว OS, security errata และ kernel update ทั้งหมดจาก yum.oracle.com โดยไม่ต้องลงทะเบียนหรือมี subscription — จุดนี้ต่างจาก RHEL และเป็นเหตุผลหลักที่เลือก Oracle Linux ได้

ไม่ได้: Ksplice (ต้องมี Premier Support) และไม่มี vendor ให้เปิดเคสเวลาเจอปัญหา ผลตรง ๆ สองข้อ:

  • ปะ kernel ต้อง reboot ทุกครั้ง → ทุกรอบ CVE ต้อง rolling drain ทั้ง cluster (ดู L12)
  • เวลาติดปัญหาต้องพึ่งทีมเองกับ community → บทที่ 13 (Troubleshooting) และการซ้อมกู้ ยิ่งสำคัญขึ้น

ทั้งสองข้อนี้ไม่ใช่การถอยหลังจากแผนเดิม เพราะ Rocky/Alma ที่เสนอไว้ก่อนหน้าก็ไม่มี vendor support และไม่มี live patching เหมือนกัน — สิ่งที่ได้เพิ่มมาจริงคือ kernel 6.12

ตัวเลือกข้อดีข้อควรระวัง

CentOS 7 (ของเดิม)—EOL แล้ว ไม่มี security patch ตั้งแต่ มิ.ย. 2024
อย่าสับสนกับ Oracle Cloud Native Environment

Oracle มี Kubernetes distro ของตัวเองชื่อ OCNE ที่ลงบน Oracle Linux ได้ — คู่มือชุดนี้ไม่ใช้ เราใช้ Oracle Linux เป็นแค่ OS ฐาน แล้วสร้าง cluster ด้วย kubeadm upstream ตามเดิม ถ้าใครเสิร์ชเจอเอกสาร OCNE ระหว่างทำ ให้ข้ามไป เพราะคนละชุดคำสั่งกันทั้งหมด

D2a เลือก kernel — UEK 8 หรือ RHCK เคาะแล้ว — UEK 8U2

Oracle Linux ต่างจาก Rocky/Alma ตรงที่ให้ kernel มาสองตัวในเครื่องเดียวกัน และเลือกได้ว่าจะบูตตัวไหน นี่คือผลกระทบที่ใหญ่ที่สุดของการย้ายมา Oracle Linux เพราะตัวเลขเวอร์ชัน kernel เป็นตัวกำหนดว่า L05 ทำอะไรได้บ้าง

ข้อสรุป — ใช้ UEK 8U2 ตาม default

ข้อนี้ปิดได้ทันทีโดยไม่ต้องรอ Phase 1 เพราะทีมยืนยันว่า ไม่มี agent ของ third-party ที่ต้องลงบน node เลย (ไม่มี backup agent, EDR หรือ monitoring agent ระดับ OS) — ซึ่งเป็นเหตุผลเดียวที่เหลืออยู่ที่จะดึงไปทาง RHCK หลังจากที่เราไม่ได้ซื้อ vendor support แล้ว

เมื่อไม่มีอะไรผูกกับ RHCK เลย ก็ไม่มีเหตุผลจะทิ้ง kernel 6.12 ไปใช้ 5.14 ทั้ง cluster บูต UEK 8U2 เหมือนกันหมด · monitoring ทั้งหมดทำที่ชั้น Kubernetes ผ่าน Prometheus + node-exporter (L09) ซึ่งรันเป็น pod ไม่ใช่ agent บน OS จึงไม่มีปัญหาเรื่อง kernel certify

D3 วิธีทำ HA ให้ control-plane endpoint เคาะแล้ว — systemd

รายละเอียดเต็มอยู่ที่ ชั้น L04 — ตัวเลือกคือ static pod (ของเดิม) / systemd service / kube-vip / hardware LB สรุปคือ แนะนำ systemd service เพราะ static pod จะหายไปพร้อม /etc/kubernetes/manifests ตอน kubeadm reset ซึ่งคือช่วงที่ต้องการมันที่สุด

D7 จะมี type: LoadBalancer ใช้ไหม เคาะแล้ว — Cilium LB-IPAM

D8 จะรองรับ stateful workload ไหม เคาะแล้ว — ไม่มี storage

  • ถ้ามี pod ฝั่งใหม่ต้องเรียกอะไรในฝั่งเดิม (หรือกลับกัน) ด้วย IP ตรง ๆ node จะเข้าใจว่าปลายทางอยู่ในเครื่องตัวเองแล้วส่งผิดที่ — เป็นอาการที่ไล่หาสาเหตุยากมาก
  • เวลาอ่าน log หรือ tcpdump จะแยกไม่ออกว่า IP ที่เห็นเป็นของ cluster ไหน

การใช้เลขคนละชุดไม่มีต้นทุนอะไรเลย และตัดปัญหาทั้งสองข้อทิ้ง จึงเป็นข้อเสนอของเอกสารนี้

MTU — เรื่องที่ลืมกันบ่อยที่สุด

VXLAN ห่อ packet เพิ่มอีก 50 bytes ถ้า node MTU = 1500 แล้วปล่อย pod MTU ไว้ที่ 1500 ด้วย จะเจออาการ “ping ผ่าน แต่ HTTP request ใหญ่ ๆ ค้าง” หรือ “TLS handshake ล้มเป็นบางครั้ง” — เป็นอาการที่หลอกให้ไปไล่หาปัญหาที่ application คู่มือใหม่ต้องมีขั้นตอนตั้ง MTU และวิธีทดสอบด้วย ping -M do -s

MetalLB — BGP modeกระจาย traffic จริงหลาย node, failover เร็วต้องให้ทีม network ตั้ง BGP peer ให้
Cilium LB-IPAM เลือกเลือก Cilium ที่ D4 อยู่แล้ว จึงไม่ต้องลง MetalLB เพิ่ม — ตัดออกไปหนึ่งระบบ · ประกาศ IP pool ด้วย CiliumLoadBalancerIPPoolต้องขอ IP pool ว่างจากทีม network เหมือนกัน · โฆษณา IP ออกนอก node ต้องเปิด l2announcements ของ Cilium

LB-IPAM ทำงานอย่างไร และต้องใช้กี่ IP

IP หนึ่งตัวผูกกับหนึ่ง Service ไม่ใช่หนึ่ง node — จำนวน IP ที่ต้องใช้จึงไม่เกี่ยวกับว่ามีกี่เครื่อง แต่เกี่ยวกับว่ามีกี่ service ที่ต้องเปิดให้คนนอก cluster เรียกถึง node ทั้ง 6 เครื่องใช้ IP ของตัวเอง (.101-.106) อยู่แล้ว และไม่เกี่ยวกับ pool นี้เลย

อยู่กับ Docker Registry ต่อ — สิ่งที่ต้องชดเชย

การคง registry เดิมไว้เป็นการตัดสินใจที่สมเหตุสมผลในรอบนี้ (ของใหม่เยอะพออยู่แล้ว) แต่ Docker Registry เปล่ามีข้อจำกัดที่ต้องรู้ตัวและมีแผนรองรับ:

  • ไม่มี vulnerability scanning — ถ้ามีข้อกำหนดเรื่องนี้ ให้รัน Trivy ที่ CI ก่อน push แทน ซึ่งได้ผลใกล้เคียงและไม่ต้องเปลี่ยน registry
  • auth เป็น htpasswd ทั้ง registry — ไม่มีสิทธิ์ระดับ project แยกไม่ได้ว่าใครอ่านอะไรได้ อย่างน้อยต้องแยก account สำหรับ pull ที่อ่านได้อย่างเดียว ออกจาก account ที่ push ได้ และห้ามใช้รหัสเดียวกับ root เหมือนของเดิม
  • TLS — ต้องยืนยันว่า registry.myhr.co.th เสิร์ฟ HTTPS ด้วย cert อะไร ถ้าเป็น self-signed ต้องวาง CA ไว้ที่ /etc/containerd/certs.d/registry.myhr.co.th/ ทุก node ถ้าเป็น HTTP ล้วนต้องประกาศ skip_verify/plain-HTTP ให้ชัด ไม่ใช่ปล่อยให้ pull ไม่ผ่านแล้วมาไล่หาทีหลัง

ตัวหน้าที่ที่เสนอ
RBACใครทำอะไรได้บ้างสร้าง role ตามหน้าที่จริง: developer (อ่าน + ดู log ใน namespace ตัวเอง), deployer, cluster-ops — cluster-admin สงวนไว้ให้ break-glass เท่านั้น

NetworkPolicyควบคุมว่า pod ไหนคุยกับ pod ไหนได้default-deny ทุก namespace แล้วค่อยเปิดเฉพาะเส้นทางที่จำเป็น — ต้องใช้ CNI ที่รองรับ (ดู D4)

Audit logบันทึกว่าใครทำอะไรกับ clusterเปิด audit policy ที่ apiserver ตั้งแต่แรกและส่งเข้า Loki — ถ้าต้องตอบคำถามผู้ตรวจสอบ นี่คือหลักฐานชิ้นเดียวที่มี
ข้อสังเกตเรื่อง PDPA

ระบบ HR เก็บข้อมูลส่วนบุคคลของพนักงาน ซึ่งโดยทั่วไปมาพร้อมข้อกำหนดเรื่องการควบคุมการเข้าถึงและร่องรอยการตรวจสอบ ผมไม่ทราบว่าองค์กรตีความข้อกำหนดไว้อย่างไร แต่รายการในตารางข้างบน (RBAC แยกตามหน้าที่, NetworkPolicy, encryption at rest, audit log) เป็นชุดพื้นฐานที่มักถูกถามหา — ควรให้ฝ่ายที่ดูแลเรื่อง compliance ช่วยยืนยันก่อนเคาะ D4 เพราะถ้าต้องมี NetworkPolicy จริง จะตัดตัวเลือก Flannel ทิ้งทันที

Helm chartทำ template ได้ มี rollback ในตัว จัดการ values ต่อ environment ได้ยังต้องมีคนรันคำสั่ง ยังไม่แก้ปัญหา drift
Argo CDgit คือแหล่งความจริงเดียว, เห็น drift ทันที, rollback = revert commit, มี UI ที่ให้สิทธิ์ dev ดู deployment ตัวเองได้โดยไม่ต้องให้ kubectlเป็นระบบเพิ่มอีกหนึ่งที่ต้องดูแล และทีมต้องเปลี่ยนนิสัยการทำงาน — ทางที่เปิดไว้สำหรับรอบถัดไป
Flux CDเบากว่า Argo, เป็น GitOps เหมือนกันไม่มี UI ในตัว ซึ่งเป็นข้อดีของ Argo ที่ทีม dev จะได้ประโยชน์มากที่สุด

มาตรฐาน manifest ที่ควรบังคับ

ดูจาก zeeme-ads/deployment.yml ของเดิมแล้ว มีหลายอย่างที่ควรเป็นแม่แบบใหม่:

รายการของเดิมที่ควรเป็น
ผู้ใช้ที่รันrunAsUser: 0non-root + readOnlyRootFilesystem + drop capabilities ทั้งหมด
resourcesไม่มีตั้ง requests/limits ทุกตัว — ไม่มีแล้ว scheduler ตัดสินใจมั่วและ node ล้มได้
probesไม่มีreadinessProbe + livenessProbe + startupProbe (Spring Boot เริ่มช้า ต้องมีตัวหลัง)
PodDisruptionBudgetไม่มีมีทุก service — ไม่งั้นตอน drain node เพื่อ upgrade จะดับพร้อมกันหมด
anti-affinityไม่มีกระจาย replica ข้าม node ด้วย topologySpreadConstraints
ResourceQuota / LimitRangeไม่มีต่อ namespace กัน namespace เดียวกินทั้ง cluster
ผลของการเลือก kubectl apply มือ — ต้องชดเชยด้วยวินัย

GitOps ไม่ได้ทำแค่เรื่องความสะดวก มันเป็นตัวบังคับให้ manifest ทุกตัวผ่านมาตรฐานในตารางด้านบน เมื่อเลือก kubectl apply มือ ตัวบังคับนั้นหายไป และมาชนกับข้อเท็จจริงจาก L12 พอดี: เราไม่มี Ksplice จึงต้อง drain ทุก node ทุกรอบ patch kernel ถ้ามี Deployment สักตัวที่ไม่มี PDB หรือมี replica เดียว rolling reboot จะทำ service ล่มจริง

สามอย่างนี้จึงต้องมีมาแทน — ไม่ใช่ของแถม:

  • manifest ทุกตัวอยู่ใน git และ apply จาก git เท่านั้น ห้าม kubectl edit บน cluster ตรง ๆ · ให้ทำเป็นข้อตกลงที่เขียนไว้ในบทที่ 11
  • ตัวตรวจอัตโนมัติแทนคน — ใส่ kubeconform + policy check (เช่น Kyverno ในโหมด audit) ที่ CI ให้ตกทันทีถ้า manifest ไม่มี PDB / probes / resources / non-root · ตัวนี้ถูกกว่า Argo CD มากและได้ประโยชน์หลักไปแล้ว
  • alert ที่จับ Deployment ที่ไม่มี PDB จาก kube-state-metrics ที่ L09 — ให้รู้ก่อนถึงรอบ patch ไม่ใช่รู้ตอน drain แล้วล่ม

ทางกลับมาเปิดไว้: ถ้าภายหลังอยากได้ Argo CD ให้ทำหลัง Phase 5 เมื่อ manifest ทุกตัวอยู่ใน git เรียบร้อยแล้ว — ตอนนั้นจะเป็นแค่การชี้ Argo ไปที่ repo ที่มีอยู่ ไม่ใช่โครงการใหญ่

Day-2 Operations

backup · cert renewal · upgrade · DR

นี่คือชั้นที่ทำให้ต้องมาตั้ง cluster ใหม่ในรอบนี้

คู่มือเดิมพา cluster ขึ้นมาได้ แต่ไม่มีบทไหนบอกวิธีทำให้มันอยู่ต่อ ไม่มี backup, ไม่มีการต่ออายุ cert, ไม่มีวิธี upgrade — พอ cert หมดอายุและเวอร์ชัน EOL ทางเดียวที่เหลือคือรื้อทำใหม่ ถ้าเลือกได้แค่บทเดียวที่จะเขียนให้ดีที่สุด ให้เลือกบทนี้

สิ่งที่ต้องมี

งานความถี่รายละเอียด
etcd snapshotทุกวัน + ก่อนแตะอะไรก็ตามetcdctl snapshot save ผ่าน CronJob เก็บออกนอก cluster และต้องมี checksum
ซ้อมกู้จริงทุกไตรมาสbackup ที่ไม่เคยกู้สำเร็จ = ไม่มี backup — ซ้อมบน cluster ทดสอบและบันทึกเวลาที่ใช้จริง
ตรวจอายุ certificateทุกเดือน + alert อัตโนมัติkubeadm certs check-expiration → ถ้าเหลือ < 60 วันให้ kubeadm certs renew all แล้ว restart static pod
Patch upgradeทุก 1-2 เดือนภายใน minor เดียวกัน ทำได้เร็ว ความเสี่ยงต่ำ
Minor upgradeปีละ 1-2 ครั้งห้ามข้าม minor — ต้องไปทีละขั้น (1.36 → 1.37 → 1.38) ลำดับคือ control plane แรกก่อน แล้วที่เหลือ แล้วค่อย worker ทีละตัวพร้อม drain
เพิ่ม/ถอด nodeตามต้องการรวมถึงวิธีออก bootstrap token ใหม่ (ของเก่าหมดอายุใน 24 ชม.) และวิธี drain ให้ปลอดภัย
Patch kernel / OS
rolling reboot		ทุก 1-2 เดือน + ทันทีเมื่อมี CVE ระดับสูงเพิ่มเข้ามาเพราะเปลี่ยนเป็น Oracle Linux · ใช้แบบฟรีจึงไม่มี Ksplice → ปะ kernel ต้อง reboot ทุกครั้ง ไม่มีทางเลี่ยง · ขั้นตอน: cordon → drain → ยก versionlock → dnf update → reboot → uncordon → ล็อก versionlock กลับทันที → ยืนยัน uname -r ตรงกับที่ตั้งใจ แล้วค่อยไป node ถัดไป
ทบทวน capacityทุกไตรมาสดู request vs usage จริงจาก Prometheus แล้วปรับ
ผลจากการใช้ Oracle Linux แบบฟรี — ไม่มี live patching

ไม่มี Ksplice แปลว่า ทุกรอบ CVE ของ kernel ต้อง reboot ทั้ง cluster ทีละ node ปีละหลายรอบ นี่เปลี่ยนจาก “งานที่เลื่อนได้” เป็น “งานประจำที่ต้องทำได้โดยไม่มี downtime” และบังคับให้สามอย่างนี้ต้องพร้อมก่อนรับ workload จริงใน Phase 4:

  • ต้องมี capacity เผื่อ N+1 — drain worker หนึ่งตัวแล้ว pod ต้องมีที่ลงครบ ถ้า worker เต็มทุกตัวจะ drain ไม่ได้เลย
  • ทุก Deployment ต้องมี PodDisruptionBudget และ replica ≥ 2 — ไม่งั้น drain จะทำ service ล่มจริง (อยู่ในมาตรฐาน manifest ที่ L11 แล้ว แต่ตอนนี้กลายเป็นข้อบังคับ ไม่ใช่ข้อแนะนำ)
  • control plane ต้องเป็น 3 ตัวจริง ๆ และ HA ต้องใช้งานได้ — reboot master ทีละตัวต้องไม่ทำให้ apiserver ขาด ซึ่งไปผูกกับ L04 ที่เสนอให้ย้าย keepalived/HAProxy เป็น systemd

เขียน rolling reboot เป็น runbook ที่มีลำดับชัดในบทที่ 12 และซ้อมหนึ่งรอบใน Phase 4 ก่อนรับ workload — ไม่ใช่มาลองครั้งแรกตอนมี CVE จริง

ก่อนอื่นเลย — ตรวจ cluster เดิมก่อน

ถ้า cluster เดิมยังรันอยู่ ให้รัน kubeadm certs check-expiration บนทุก master ก่อนทำอะไรทั้งสิ้น cert ของ kubeadm มีอายุ 1 ปี และจะต่ออายุอัตโนมัติเมื่อ upgrade เท่านั้น — cluster ที่ตั้งเมื่อ 2-3 ปีก่อนและไม่เคย upgrade มีโอกาสสูงที่ cert หมดอายุไปแล้ว ซึ่งจะเปลี่ยนแผนการย้าย workload ทั้งหมด

แผนดำเนินการ

หัวใจของแผนนี้อยู่ที่ Phase 3 — การรื้อ lab แล้วสร้างใหม่จากคู่มือที่เขียนโดยให้คนที่ไม่ได้เขียนเป็นคนทำ นั่นคือขั้นตอนเดียวที่พิสูจน์ได้ว่าคู่มือใช้งานได้จริง ไม่ใช่แค่บันทึกความจำของคนเขียน

Phase 0 — เคาะและสำรวจ

~1 สัปดาห์

ตัดสินใจครบทุกข้อแล้ว เหลืองานสำรวจ: ตรวจ cert ของ cluster เดิม (kubeadm certs check-expiration) · หมุน credential ที่รั่วในเอกสารเดิม · ทำ VM template ของ OL 9.8 ที่ versionlock kernel แล้ว พร้อมแผน partition ใหม่ (ย้าย /home) · วัด fsync ของ disk ด้วย fio เพื่อตัดสินว่าต้องขอ VMDK แยกให้ etcd ไหม · ยืนยันว่า registry เป็น HTTP หรือ HTTPS · ขอ VIP และ LB-IPAM pool จากทีม network

Phase 1 — Lab

~2 สัปดาห์

สร้าง lab 2 master + 2 worker บน OL 9.8 + UEK 8U2 (ใช้เครื่องฝึกอบรมเดิมที่ 192.168.50.180-183 ได้ แต่ต้องใช้ VIP, virtual_router_id และ LB-IPAM pool คนละชุดกับ production เพราะอยู่ L2 domain เดียวกัน) · เดินทีละชั้น L00→L06 · จดทุกอย่างที่ติดขัดขณะทำ — บันทึกนี้จะกลายเป็นบทที่ 13 โดยตรง

Phase 2 — เขียนคู่มือฉบับร่าง

~2 สัปดาห์

เขียนบท 00-08 จากสิ่งที่ทำจริงใน Phase 1 · ใส่ verify step ทุกขั้น · ทำ versions.env และ Ansible playbook

Phase 3 — ทดสอบคู่มือ ขั้นตอนสำคัญ

~1 สัปดาห์

รื้อ lab ทิ้งแล้วสร้างใหม่ตามคู่มือ โดยให้คนที่ไม่ได้เขียนเป็นคนทำ · ทุกจุดที่คนทำต้องถามคนเขียน = ช่องโหว่ในคู่มือ ต้องแก้ · เกณฑ์ผ่านคือ ทำจนจบได้โดยไม่ต้องถาม

Phase 4 — Production

~2 สัปดาห์

สร้าง cluster จริง 3 master + worker ตามคู่มือที่ผ่าน Phase 3 · เพิ่มบท 09-12 (observability, security, delivery, day-2) · ตั้ง backup และ alert ให้ทำงานจริงก่อนรับ workload · ซ้อม rolling reboot ปะ kernel หนึ่งรอบ — จำเป็นเพราะไม่มี Ksplice ให้ใช้ ต้องพิสูจน์ว่า drain ทั้ง cluster ได้จริงตั้งแต่ตอนที่ยังไม่มี workload

Phase 5 — ย้าย workload และส่งมอบ

~2-3 สัปดาห์

ย้าย microservices ทีละตัวตามแม่แบบใหม่ (แก้ runAsUser, ใส่ probes/resources/PDB) · ซ้อมกู้ etcd หนึ่งรอบ · อบรมทีมด้วยคู่มือชุดใหม่ · ปลด cluster เดิม

ความเสี่ยงและสิ่งที่ต้องยืนยัน

ความเสี่ยงผลกระทบวิธีรับมือ
cert ของ cluster เดิมหมดอายุแล้วย้าย workload แบบค่อยเป็นค่อยไปไม่ได้ ต้องเร่งสร้างของใหม่ตรวจใน Phase 0 ทันที ถ้าหมดจริงยังกู้ได้ด้วย kubeadm certs renew all ตราบใดที่ CA ยังไม่หมด (CA อายุ 10 ปี)
มีนโยบายให้ลง EDR / backup agent บน node ทีหลังagent พวกนี้จำนวนไม่น้อย certify เฉพาะ RHCK — ถ้าต้องย้าย kernel ทั้ง cluster ตอนมี workload จริงแล้ว จะแพงกว่าตัดสินตอนนี้มากตอนนี้ยืนยันแล้วว่าไม่มี agent จึงปิด D2a เป็น UEK ได้ · ถ้าอนาคตมีนโยบายเพิ่ม ให้กลับมาทบทวน D2a ก่อนลง ไม่ใช่ลงแล้วค่อยแก้ · ระบุเงื่อนไขนี้ไว้ในภาคผนวก D (บันทึกความต่างและเหตุผล)
node บูตคนละ kernel กันโดยไม่รู้ตัวอาการ network ต่างกันเป็นราย node — เป็นบั๊กที่หาสาเหตุยากที่สุดแบบหนึ่งdnf versionlock ที่ kernel-uek ทุกเครื่อง · ใส่ uname -r เป็น verify step ในบทที่ 02 · ทำ alert ที่ Prometheus เทียบ node_uname_info ข้าม node
ไม่มี vendor support ให้เปิดเคส (ใช้ OL แบบฟรี)เจอบั๊กระดับ kernel หรือ driver แล้วไม่มีใครให้พึ่ง ต้องแก้กันเองหรือรอ upstreamยอมรับความเสี่ยงนี้ — Rocky/Alma ก็ไม่ต่างกัน · ชดเชยด้วยการทำบทที่ 13 ให้ละเอียดและยึด default ของ distro ให้มากที่สุด อย่าไป custom kernel parameter หรือ out-of-tree module ถ้าไม่จำเป็นจริง เพราะจะไม่มีใครเคยเจอเคสเดียวกัน
ไม่มี Ksplice → ต้อง reboot ทุกรอบ patch kernelถ้า capacity ไม่พอหรือไม่มี PDB จะ drain node ไม่ได้ กลายเป็นเลื่อน patch ออกไปเรื่อย ๆ จนค้าง CVEบังคับ N+1 capacity, PDB และ replica ≥ 2 ให้เสร็จก่อนรับ workload ใน Phase 4 · ซ้อม rolling reboot หนึ่งรอบใน Phase 4 (ดู L12)
Cilium รับภาระ 3 หน้าที่พร้อมกัน (CNI + kube-proxy + LB-IPAM)Cilium มีปัญหาทีเดียว = pod network, Service และ LoadBalancer ดับพร้อมกันหมด · ไม่มี kube-proxy ให้ถอยกลับไปใช้เพราะไม่ได้ติดตั้งไว้เลยนี่คือราคาของการตัดชิ้นส่วนออก ซึ่งคุ้มถ้าทีมคุมมันได้ · Phase 1 ต้องพิสูจน์ว่าทีม debug Cilium ได้จริง ไม่ใช่แค่ติดตั้งผ่าน · แผนสำรองคือ Calico + kube-proxy nftables + MetalLB ซึ่งต้องตัดสินก่อนจบ Phase 3 เพราะเปลี่ยนหลังจากนั้นคือรื้อ L05-L06 ทั้งชั้น
ไม่มี GitOps บังคับมาตรฐาน manifest (D9 = kubectl apply)Deployment ที่ไม่มี PDB หรือมี replica เดียวจะหลุดขึ้น production แล้วไปดับตอน drain node รอบ patch kernel ซึ่งเกิดทุก 1-2 เดือนใส่ kubeconform + policy check ที่ CI ให้ตกทันทีถ้า manifest ไม่ครบมาตรฐาน · ทำ alert จับ Deployment ที่ไม่มี PDB · ดูรายละเอียดที่ L11
